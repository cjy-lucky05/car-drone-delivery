# car-drone-delivery · 车-机协同末端配送系统

> 一台**地面小车** + 一台**无人机**协同完成校园末端快递配送：
> 无人机把包裹投放到站点库位，小车自动前往取货并送达。
> 研究重点是 **多智能体协同调度机制** 与 **跨 ROS 版本的分布式通信**。

---

## 这是什么

末端配送的最后一公里，可以用「无人机 + 地面车」分工来完成：
无人机快、不堵车，适合在站点间快速投放；小车稳、载重大，适合从站点拉到用户手里。

本项目的关键不在"能飞"或"能走"，而在这两件事：

1. **多台设备怎么协同** —— 谁先动、谁等谁、状态怎么共享
2. **不同版本/不同网络的设备怎么通信** —— 小车跑 ROS1、机载端跑 ROS2，还分别在校园网和校外

配套：仓库中另有一份《ROS 接口清单》文档，记录了地面车侧全部可调用的 ROS 接口。

## 系统架构

系统只有三个角色，设备之间**不直接对话**，全部通过中间件转发：

```
┌──────────────────────────┐
│  设备端（小车 / 机载端）   │   上报状态与事件 / 接收指令
└───────┬──────────────────┘
        │  cjy/{设备}/report   （设备的"嘴"：汇报）
        │  cjy/{设备}/cmd      （设备的"耳朵"：指令，单播）
        ▼
┌──────────────────────────┐
│  MQTT broker（mosquitto） │   ★ 只转发消息，不做决策（相当于邮局）
└───────┬──────────────────┘
        ▼
┌──────────────────────────┐
│  平台 hub.py（本仓库）     │   维护库位表/任务表 → 做决策 → 下发指令
└──────────────────────────┘
```

**为什么要有"平台"**：如果让设备互相喊话，"库位有没有货""这单该谁取"就得每台设备各维护一份，
很容易不一致。由平台统一维护，全局只有一份真相。

## 核心机制

### 1. 库位分配用「环形队列」（FIFO）

无人机投放前先问平台「放哪个库位」，平台按环形队列分配：

```
投放 → 放到【最后一个有货位的下一个位置】
取货 → 从【最前面的有货位】取
```

**为什么不能"找第一个空位"**：那样 A 被取空后会立刻又放 A，
导致小车永远在取 A、B/C 里的旧货被跳过（库位饿死）。

### 2. 平台权威

设备上报什么**不作数**：库位分配由平台决定，若设备上报的与平台记录不一致，
**以平台为准**并打印警告。

### 3. 固定分工 + 每站点独立 FIFO 队列 + 忙闲感知

```
站点1 的任务 → 只派给 1 号车；站点2 → 2 号车……
每个站点一条独立队列，按入库顺序排队
车在忙 → 任务继续排队；车上报 idle（空闲）→ 才派下一个
```

★ "车空闲才派单"这个**拉模型**同时解决了两件事：不会派给忙车（顺序不会乱）、
也不会在设备离线时把指令丢掉。

### 4. 跨系统桥接

小车侧有一个桥接节点，把 MQTT 指令翻译成 ROS 动作（导航 / 机械臂 / 夹爪），
再把执行结果回报给平台。设备端与平台互相不知道对方的技术栈。

## 快速开始

### 1. 准备配置

```bash
cp config.example.py config_local.py
# 编辑 config_local.py，填入 MQTT 服务器地址和各账号密码
```
> `config_local.py` 已在 `.gitignore` 中，**不会被提交**。
> 每台机器（PC / 服务器 / 机载端 / 小车）各放一份自己的。

### 2. 启动平台（在服务器上）

```bash
pip3 install --target=./libs paho-mqtt     # 依赖装本地，不动系统
python3 平台/hub.py
```

### 3. 启动设备端

```bash
# 机载端（无人机侧）——只需上报两个事件
python3 设备端/device_client.py --role drone --event ask_slot --site 1

# 小车侧 ——桥接节点常驻，接收平台指令
python3 设备端/mqtt_bridge_node.py --dry   # --dry = 干跑模式（不真导航，先验证链路）
```

### 4. 跑仿真

```bash
python3 仿真/tsp_demo.py
```
